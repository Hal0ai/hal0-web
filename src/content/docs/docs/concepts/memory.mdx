hal0 can give your platform a persistent **memory** — a store of facts that both
the operator surfaces and the bundled agent can write to and recall from. It's a
deliberate, opt-in subsystem: powerful when you want it, and completely absent
when you don't.

## What memory is

The memory subsystem is an engine-neutral layer behind two surfaces: the
`/api/memory/*` REST routes (which the dashboard's Memory view uses) and the
`/mcp/memory` MCP server (which agents and external tools use). Both speak to the
same provider, so a fact written by an agent over MCP is the same fact the
dashboard shows.

![Memory interface showing stored facts and recall](/screenshots/memory-view.png)
*Memory view in the hal0 dashboard*

The default engine is **Hindsight** — a memory service that powers the shared
operator and agent "brain." Since v0.9.8, **Honcho v3** is also available as a
unified memory provider, supporting both Hindsight and Honcho backends through
the same `/api/memory/*` and `/mcp/memory` surfaces. The provider is selected
from `[memory].enabled` in `hal0.toml` (default `true`), so the surfaces stay
the same regardless of which engine backs them.

![Memory graph visualization showing relationships between facts](/screenshots/memory-graph.png)
*Fact relationships in the knowledge graph*

<Aside type="note">
The memory layer is engine-neutral by design. Hindsight is the default, but the
provider is selected from config, so the surfaces (REST + MCP) stay the same
regardless of which engine backs them.
</Aside>

## Memory is enabled by default

In v0.9.8, memory is **enabled by default** via `[memory].enabled = true` in
`hal0.toml`. This replaces the old `HAL0_MEMORY_ENABLED` environment variable
(removed in v0.9.8). When memory is disabled:

- No memory provider is built.
- Every downstream caller degrades to a no-op or a clean error — the
  `/api/memory/*` routes, the `/mcp/memory` server, the agent's memory provider,
  and the per-agent memory stats all handle the absent provider gracefully.
- The dashboard hides the Memory navigation.

Flipping the setting is the *entire* toggle — no code change, and the behaviour
is identical on fresh and upgraded installs.

<Aside type="caution">
To disable memory, set `[memory].enabled = false` in `hal0.toml` and restart
`hal0-api`. Until you enable it, the memory surfaces are inert.
</Aside>

## What memory powers

When enabled, memory becomes the shared brain that ties the platform together:

<CardGrid>
  <Card title="The agent's recall" icon="comment">
    The bundled agent reads and writes memory through MCP, so it can remember
    context across conversations — scoped to a per-agent namespace.
  </Card>
  <Card title="Operator memory" icon="document">
    The dashboard Memory view and the `/api/memory/*` routes let you add, search,
    and prune facts directly.
  </Card>
  <Card title="Namespaced writes" icon="setting">
    Callers identify themselves (via the `X-hal0-Agent` header), so private
    writes land in the right per-agent namespace rather than a shared pool.
  </Card>
</CardGrid>

## Honcho v3: the unified memory provider

Since v0.9.8, **Honcho v3** is available as a unified memory provider that
supports both Hindsight and Honcho backends through the same surfaces. The
provider is selected from `[memory].enabled` in `hal0.toml`.

<Aside type="note">
Honcho v3 provides a single memory API that works with both Hindsight banks
and Honcho's native storage. This means operators can migrate from Hindsight
to Honcho (or vice versa) without changing the REST or MCP surfaces.
</Aside>
