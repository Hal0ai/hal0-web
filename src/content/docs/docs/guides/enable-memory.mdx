hal0's memory subsystem is **enabled by default** in v0.9.8. It gives
agents a persistent recall store (Hindsight by default) plus an optional
knowledge-graph extraction layer. The toggle is a single config setting —
no environment variable, no reinstall.

<Aside type="note">
Memory ships enabled (`[memory].enabled = true`) so behaviour is identical on
fresh and upgraded installs. Every downstream caller — the admin MCP tools, the
`/api/memory/*` routes, the agent memory provider — degrades to a no-op or
`503` when memory is off, so flipping the setting is the whole toggle.
</Aside>

## Turn it on

In v0.9.8, memory is enabled by default. If you previously disabled it with
`HAL0_MEMORY_ENABLED=0`, you can re-enable it by setting `[memory].enabled =
true` in `hal0.toml`:

<Steps>

1. **Edit the config.** Open `/etc/hal0/hal0.toml` and ensure the memory
   section is present and enabled:

   ```toml
   [memory]
   enabled = true
   ```

2. **Restart the API** so `create_app` constructs the memory provider:

   ```sh
   sudo systemctl restart hal0-api
   ```

3. **Confirm it's wired.** The memory status endpoint now responds with
   real state instead of degrading:

   ```sh
   hal0 memory status
   ```

</Steps>

When the setting is enabled, hal0 builds the memory provider from your config.
The default engine is **Hindsight**; if the Hindsight service is
unreachable at startup, hal0 logs a warning and degrades to a local
pgvector-backed provider rather than failing startup.

## Turn it off

To disable memory entirely:

```toml
[memory]
enabled = false
```

Then restart `hal0-api`. All memory surfaces (REST, MCP, dashboard, agent)
will degrade to no-ops.

## The graph-extraction gate

Storing recall items is one thing; running an LLM over them to extract a
knowledge graph is heavier and separately gated. Control it with the
`hal0 memory graph` sub-app (a thin client over `/api/memory/graph`).

![Memory view showing live graph extraction status and counters](/screenshots/memory-view.png)
*Live memory and graph-extraction dashboard in hal0.*

<Tabs>
<TabItem label="Status">

```sh
hal0 memory graph status
hal0 memory graph status --json
```

Shows whether extraction is on, the dispatch route, the configured
upstream, and counters (builds OK, errors, in-flight, last build / error).

</TabItem>
<TabItem label="Enable">

```sh
# extract via a configured external upstream
hal0 memory graph enable --route upstream \
  --provider openrouter --model anthropic/claude-3.5-sonnet

# or route to a local slot
hal0 memory graph enable --route primary
hal0 memory graph enable --route agent
```

`--route` is one of `upstream`, `primary`, or `agent`. When
`--route=upstream`, both `--provider` and `--model` are required (the
server enforces this too, so scripts hitting the API directly get the same
validation).

</TabItem>
<TabItem label="Disable">

```sh
hal0 memory graph disable
```

Turns extraction off and cancels any in-flight build.

</TabItem>
</Tabs>

## Migrate a legacy store

If you previously ran the Cognee-backed memory store, preview a migration
into Hindsight banks:

```sh
hal0 memory migrate --dry-run
hal0 memory migrate --dry-run --cognee-dir /var/lib/hal0/memory/cognee
```

The report shows rows total / mapped / unmapped and whether it's a no-op.

<Aside type="caution">
Migration is **dry-run only** today — it reports the plan without writing.
Passing `--no-dry-run` exits with a "not yet implemented" error.
</Aside>
