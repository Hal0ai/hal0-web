hal0 exposes two voice directions through OpenAI-compatible endpoints:

- **Speech-to-text** (`POST /v1/audio/transcriptions`) — Moonshine container on CPU,
  or the FLM trio on the NPU.
- **Text-to-speech** (`POST /v1/audio/speech`) — two backends: Kokoro ONNX container
  on CPU (lightweight, English) or Qwen3-TTS CustomVoice on ROCm/GPU (multilingual, richer voices).

Both are children of the **`voice`** capability: `voice.stt` maps to the
`stt` slot and `voice.tts` maps to the `tts` slot.

## Enable the voice capability

Voice is opt-in. Enable each direction from the dashboard's capability
picker, or by POSTing a partial selection to the capability API. The body
accepts any subset of `{ backend, provider, model, enabled }`:

<Tabs>
<TabItem label="Speech-to-text (CPU, Moonshine)">

```sh
curl -X POST http://localhost:8080/api/capabilities/voice/stt \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "backend": "cpu", "provider": "moonshine"}'
```

</TabItem>
<TabItem label="Speech-to-text (NPU, FLM trio)">

```sh
curl -X POST http://localhost:8080/api/capabilities/voice/stt \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "backend": "npu"}'
```

</TabItem>
<TabItem label="Text-to-speech (CPU, Kokoro)">

```sh
curl -X POST http://localhost:8080/api/capabilities/voice/tts \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "backend": "cpu", "provider": "kokoro"}'
```

</TabItem>
<TabItem label="Text-to-speech (ROCm/GPU, Qwen3-TTS)">

```sh
curl -X POST http://localhost:8080/api/capabilities/voice/tts \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "backend": "rocm", "provider": "qwen3-tts"}'
```

</TabItem>
</Tabs>

The response is `{ "ok": true, "selection": { ...current selection... } }`.

<Aside type="note">
Both Moonshine and Kokoro are containerized servers running on CPU — they do not use ROCm or the NPU.
The NPU transcription path uses the FLM container, not Moonshine. Qwen3-TTS runs on ROCm/GPU and
requires `amdgpu` access (`/dev/kfd`, `/dev/dri/amdgpu`).
</Aside>

### How the NPU path differs

Choosing `backend=npu` for `voice.stt` does **not** spawn a standalone
process. Instead it drives the **FLM trio** — one `flm serve` anchor
process serving chat coresident with transcription (and embeddings). The
orchestrator toggles the anchor's `asr` flag and writes a
`type=transcription` slot record for dispatch gating; the live anchor is
reloaded so the change takes effect. This is why NPU transcription needs
the FLM chat anchor to be loaded.

## Transcribe audio (speech to text)

Send a multipart upload with the audio file and a required `model` field.
The raw multipart bytes are forwarded unchanged to the upstream:

```sh
curl -X POST http://localhost:8080/v1/audio/transcriptions \
  -F 'file=@recording.wav' \
  -F 'model=<your-stt-model>'
```

The `model` form field is **required**; omitting it returns **400**
(`request.missing_model`) rather than a misleading 404.

## Synthesize speech (text to speech)

Send a JSON body with `model`, `input`, and `voice`. The response is the
audio stream:

```sh
curl -X POST http://localhost:8080/v1/audio/speech \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<your-tts-model>",
    "input": "Hello from hal0.",
    "voice": "<voice-id>"
  }' \
  --output speech.wav
```

As with transcription, `model` is required — a missing or empty `model`
returns **400** (`request.missing_model`).

### Choosing a TTS backend

hal0 supports two TTS engines, depending on which provider you select for the `tts` slot:

<Tabs>
<TabItem label="Kokoro-82M (CPU, ONNX)">

Kokoro-82M is a lightweight ONNX model that runs entirely on CPU. It needs no
GPU or NPU access. Use it when you want:

- Minimal resource footprint (doesn't compete with LLM slots for VRAM).
- English-only speech synthesis.
- 54 American and British English voice presets (`af_*`, `am_*`, `bf_*`, `bm_*`).
- Quick cold-start times (the ONNX runtime loads in under a second).

Model: `kokoro`. Default voice: `af_heart`. Output format: MP3 (default) or WAV.

```sh
# Quick test
curl -s -X POST http://localhost:8084/v1/audio/speech \
  -H 'Content-Type: application/json' \
  -d '{"model":"kokoro","input":"Hello world.","voice":"af_bella","response_format":"wav"}' \
  -o kokoro_test.wav
```

</TabItem>
<TabItem label="Qwen3-TTS CustomVoice (ROCm/GPU)">

Qwen3-TTS is a 1.7B-parameter transformer model that runs on ROCm via the
`ghcr.io/hal0ai/hal0-toolbox-qwen3tts` container. It uses the AMD iGPU and
requires `--device /dev/kfd --device /dev/dri/amdgpu`. Use it when you want:

- **Multilingual** output — 10+ languages with native pronunciation (the `language`
  field auto-detects or accepts a specific ISO code).
- **Richer, more expressive voices** than ONNX-based synthesis.
- Production-quality speech with natural prosody and intonation.

Model: `qwen3-tts`. Default voice: `Ryan`. Output format: WAV.

Considerations:
- Uses GPU VRAM — may contend with LLM slots under heavy concurrent load.
- Slightly higher latency on cold calls than Kokoro (model loading).
- Requires `amdgpu` kernel module to be loaded.

```sh
# Quick test
curl -s -X POST http://localhost:8084/v1/audio/speech \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-tts","input":"Hello world.","voice":"Ryan","response_format":"wav"}' \
  -o qwen3_test.wav
```

</TabItem>
</Tabs>

<Aside type="note">
The hal0 orchestrator ships a unified TTS bridge script (`hal0-voice-tts.py`) that
reads the active engine from a state file and automatically falls back if one backend
is down. Flip between Qwen3 and Kokoro at runtime without restarting slots or agents.
</Aside>
