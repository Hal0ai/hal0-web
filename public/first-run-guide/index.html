The guided path

Set up in the dashboard

Once hal0 is installed, everything below happens in your browser at http://localhost:8080 — the control plane hal0-api serves the dashboard on the same port as the API.

1

Open the dashboard

Point a browser on your LAN at the host on port 8080. You’ll land on the overview: slot status, live hardware metrics, and quick actions. This is home base for every step that follows.

💡 Tip: press ⌘ K / Ctrl K anywhere to open the command palette and jump to any tab, slot, or action by name.
2

Add your models — the Models tab

hal0 ships with no models by design — you add exactly what you want. Models live in a local registry: the single source of truth for Hugging Face coordinates, digests, and filenames. The Models tab is where you populate it — search Hugging Face, pull curated aliases, and watch progress badges. This is your first stop after opening the dashboard.

  1. Browse or search. Use the curated catalogue, or search Hugging Face directly from the tab to find a model and its pullable GGUF variants.
  2. Pull. Click Pull on a model. The download runs in the background with a live progress bar; the row shows a status badge (queued → running → completed).
  3. Register on-disk weights — already have a GGUF on the host? Register it into the registry without re-downloading.
  4. Assign to a slot. A completed model can be set as a slot’s default from here or from the Slots tab (next step).
Gated or private models? Add a token under Settings → Secrets → HuggingFace token — it applies live, no restart.
3

Profiles — the how-to-run recipes

A profile is a reusable runtime template: the container image, bench-tuned launch flags, and an MTP (speculative-decoding) toggle. Many slots can share one tuned profile. The Profiles tab shows the seed profiles that ship with hal0:

  1. Read the seed cards. Each shows its target device, runtime family, and reference throughput. These cover a fresh install out of the box.
  2. Seeds are immutable. To customise one, click Clone, give it a new name, and edit the copy’s flags.
  3. Tune MTP. A profile’s speculative-decoding bundle is a single toggle; any slot can override it with its own Auto / On / Off control.
4

Slots & lifecycle — the Slots tab

A slot is one running inference endpoint: a model, a device, a profile, and a port. The Slots tab lists every slot with a live state badge, its model, device, and port.

  1. Create a slot. Click New slot and fill the picker: name, type (llm · embedding · reranking · transcription · tts · image), model, device, and context size. hal0 derives a coherent default profile from the device.
  2. Open a slot for its detail panel — live status alongside the persisted config — to edit the model, port, or context size.
  3. Drive it with Load · Restart · Unload right from the card or detail panel.

Loading a slot walks it through the lifecycle state machine. The Slots view animates each transition:

offline
pulling
starting
warming
ready → serving ✓

Idle slots drop to idle and free the GPU; a failed launch shows error with the reason inline.

⚠️ Single-GPU boxes (Strix Halo): slots share one iGPU through an arbiter. Load what you need and unload the rest — the Unified Memory bar shows how much headroom is left.
5

Capabilities — wire roles to slots

Capabilities are the operator-friendly overlay: instead of hand-configuring each slot, you pick a capability and its child, and hal0 reconciles the real slot for you. Toggling one on loads its slot; off unloads it.

CapabilityChildren → underlying slot
embedembed → embed · rerank → embed-rerank
voicestt → stt · tts → tts
imgimg → img
visionvision → vision
  1. Toggle a capability on and pick its child’s model and backend from the card.
  2. Apply. hal0 writes capabilities.toml and the affected slot config together — atomically, so they can never drift — then drives the slot lifecycle for you.
  3. Chat is different. It’s not a capability overlay — the chat slot is configured directly in the Slots tab.
You’re live. Point any OpenAI SDK at http://localhost:8080/v1, or open the prewired chat UI (OpenWebUI) on port 3001.

The terminal path

The same flow, on the CLI

Every dashboard action has a one-line equivalent. The hal0 CLI is a thin client over the same API on port 8080, so the CLI and dashboard always agree — ideal for scripted or headless hosts. Here are the five stages.

0

Install & bring up the API

Get the control plane running and verify the host is ready. hal0 ships with no models by design — you add your own next, in Stage 1.

API on :8080
bash
$ hal0 --version                          # → hal0 0.9.2
$ hal0 doctor                             # re-run installer preflight checks
$ sudo systemctl enable --now hal0-api    # bring up the control plane on :8080
$ hal0 status                             # confirm the daemon is alive on :8080
💡 Already running? The installer normally enables hal0-api.service for you — the command above just confirms it’s up. hal0 ships with no model stack, so add exactly the models you want in the next stage.
1

Add your first models

Pull a curated model by its alias. Downloads run as a background job on the daemon with a live progress bar.

bash
$ hal0 model pull qwen3-4b        # download from Hugging Face
$ hal0 model list                 # what you have + what you can pull
$ hal0 model show qwen3-4b        # inspect metadata

# already have weights on disk? register instead of downloading:
$ hal0 model register /mnt/ai-models/MyModel/model.gguf
Done when — hal0 model list shows your model in the local registry.
2

Create & assign profiles

A profile is the “how to run it” recipe — container image, engine flags, backend (vulkan/rocm/cpu), and whether MTP speculative decoding is on. Profiles are shared: any slot can name the same one.

profile · saber-fpx
image  = …:rocmfpx
backend = vulkan
flags  = -fa on -ngl 999 …
mtp    = true
named by
slot · utility
"profile" : "vkfpx-moe"
"model"   : "qwen-…-35b"
"port"    : 8081
bash
# 1) list existing profiles — a seed one often already fits
$ curl -s http://127.0.0.1:8080/api/profiles | jq '.[].name'

# 2) create a custom profile by editing config, then reload
$ hal0 config edit            # add a [profile.my-profile] block
$ hal0 config validate        # check before applying
$ hal0 config reload          # daemon re-reads the TOMLs
Copy an existing block like [profile.saber-fpx] and tweak flags/backend rather than writing one from scratch. A slot references a profile by name via its "profile" field.
Done when — your profile appears in /api/profiles and hal0 config validate passes.
3

Create your first slot

A slot is a named worker bound to a port, a type, a backend, and a model. Creating it writes config; it stays offline until you load it.

bash
$ hal0 slot create primary \
    --type llm \
    --model qwen3-4b \
    --hardware vulkan \
    --ctx-size 8192

# other slot types work the same way
$ hal0 slot create embed --type embedding -m qwen3-embedding-0-6b-q8-0
$ hal0 slot create stt   --type transcription -m whisper-v3:turbo
FlagMeaningDefault
--typellm · embedding · reranking · transcription · tts · imagellm
--model / -mModel ref to assign (required)—
--hardwarevulkan · rocm · cpuauto-detected
--port / -pTCP portauto, 8081–8099
--ctx-sizeContext window4096
bash — re-point a slot later
$ hal0 model assign qwen3-4b --slot primary   # set default, no reload
$ hal0 slot edit primary --ctx-size 16384       # tweak config fields
Done when — hal0 slot list shows your slot (reads offline until loaded).
4

Bring slots online

Loading starts the engine and occupies the port. Here’s the slot lifecycle:

offline
slot load
loading
ready
serving ✓
slot unload
offline
bash
$ hal0 slot load primary            # start the engine
$ hal0 slot list                   # state: offline → serving
$ hal0 slot status primary          # includes config-drift warnings
$ hal0 slot logs -f primary         # follow startup logs live

# everyday controls
$ hal0 slot swap primary -m qwen3-8b  # change model, survives restart
$ hal0 slot restart primary         # unload then load
$ hal0 slot unload primary          # free the GPU / port
⚠️ Single-GPU boxes (Strix Halo): the iGPU is time-shared across slots — loading several heavy slots at once contends for memory bandwidth. Load what you need; unload what you don’t.
Done when — hal0 slot list shows serving and logs report the model loaded.
5

Wire a capability — optional but recommended

Slots are plumbing; capabilities are the roles apps actually ask for. Mapping agent → your slot means requests to the hal0/agent role route there — no app needs to know the port.

role · agent slot · primary
role · voice.tts slot · tts

Roles live in /etc/hal0/capabilities.toml — agent, utility, embed, rerank, voice.tts, img, vision. Assign via the dashboard picker, or repair/validate selections on the CLI:

bash
$ hal0 capabilities migrate --dry-run   # preview changes
$ hal0 capabilities migrate             # snap selections to legal slots
